# Установка и ручное обслуживание

Используйте установщик из полного checkout проекта или entry point из README. Compose, Xray, Angie и `.env` генерируются из одной версии проекта: эта инструкция намеренно не содержит отдельных копий YAML/JSON, которые могли бы расходиться с шаблонами.

## Перед установкой

Нужна поддерживаемая Debian/Ubuntu, systemd, root-доступ, свободное место для образов и резервных копий, корректные A/AAAA всех SNI и консоль провайдера. После обновления ядра сначала перезагрузите VPS. Сохраните действующую SSH-сессию до проверки нового входа.

```bash
sudo apt-get update
sudo apt-get upgrade
sudo reboot
```

На свежей системе выполните команды установки из README. Не сбрасывайте firewall и не отключайте проверку подписей APT для исправления ошибки WARP. Если старый установщик оставил публичные файлы с правами `0600`, новый исправит их доступность перед обновлением пакетов.

## Где находятся файлы

| Путь | Назначение |
|---|---|
| `/opt/xray-vps-setup/current` | Ссылка на активную конфигурационную версию |
| `/opt/xray-vps-setup/docker-compose.yml` | Ссылка для обычных Compose-команд |
| `current/state.json` | Сохранённая идентичность и настройки, `0600` |
| `current/credentials.txt` | Реквизиты и ссылки всех standalone SNI, `0600` |
| `current/client.json` | Standalone-клиент с SOCKS-авторизацией |
| `current/images.lock` | Digests выбранных образов |
| `marzban_lib` | Постоянная база/данные Marzban |
| `node_data` | Постоянные TLS certificate/key node |
| `backups` | Конфиги и снимок базы перед переключением |
| `last-transaction/deployment.json` | Журнал последнего переключения |

Открывайте эти пути через `sudo`: каталоги проекта приватные. Конфиги содержат Reality private key, UUID, пароли и токены незавершённых API-транзакций. Не отправляйте их целиком в публичные логи.

## Диагностика

```bash
sudo docker compose -p xray-vps-setup -f /opt/xray-vps-setup/docker-compose.yml ps
sudo docker compose -p xray-vps-setup -f /opt/xray-vps-setup/docker-compose.yml logs --tail=100
sudo bash vps-setup.sh check
sudo systemctl status xray-setup-firewall.service
sudo ss -ltnp
```

Контейнеры имеют ограниченные по размеру логи. У Xray включён warning-level; Angie пишет ошибки в stderr. TLS/HTTP проверяются для каждого SNI с проверкой доверия сертификату. Отказ DNS/ACME либо restart loop не выдаётся за успешную установку. Для панели отдельно проверяются вход администратора и сохранение hosts; для node — реальное подключение панели.

## Безопасное изменение

Для смены SNI, ACL и split-IP используйте `reconfigure`, для восстановления с прежними настройками — `repair`. Они не ротируют ключи и пароли. Repair использует сохранённые digests; обновление образов/версии ядра — отдельное решение, а не скрытая часть ремонта.

Панель может сохранять своё core config через API. При repair дополнительные serverNames узлов, посторонние inbounds и правила сохраняются. Изменение ключей или контракта управляемых inbounds вне установщика вызывает отказ вместо неявного восстановления старых ключей. Сначала согласуйте состояние и сохраните резервную копию.

Не редактируйте private/public Reality keys независимо друг от друга. В выводе Xray 26.3.27 `PrivateKey` — серверный секрет, `Password (PublicKey)` — публичный параметр клиента. UUID и непустой shortId также должны совпадать с сервером. Для панели управляйте пользователями через базу/UI, а не статическим `clients` в JSON.

При переносе базы обязательно сохраните **весь** каталог `marzban_lib` при остановленной панели. Он монтируется в `/var/lib/marzban`; пересоздание контейнера не должно удалять базу. Xray executable/assets панели указывают на `/code/xray-core`, node — на `/tmp/xray-core`. Панель использует localhost TCP 8000, который соответствует upstream Angie; UDS в данной схеме не включайте.

## Прерванное переключение

```bash
sudo bash vps-setup.sh recover
```

Recovery использует сохранённые SSH/firewall/Compose конфиги и предыдущую версию. При изменениях удалённой панели потребуется повторная авторизация; если администратор изменил конфиг после установщика, автоматический откат откажется затирать эти изменения. Сопоставьте private journal `api-transaction.json` с текущими настройками в UI. Если ответ POST создания node потерян, проверьте список nodes; неизвестное создание автоматически не удаляется.

Не восстанавливайте старый снимок базы поверх работающей панели без отдельного решения: можно потерять пользователей и статистику, созданных после снимка. Recovery конфигурации не подменяет базу автоматически. Новые пакеты и SSH-аккаунт также остаются установленными.

При исчерпании диска освобождайте место осознанно. Не удаляйте активную версию, предыдущую версию незавершённой транзакции, её backup, `marzban_lib` или `node_data`. Проверьте объём `releases`/`backups`; автоматической очистки резервных копий нет.

SSH-подготовку завершайте только через команду подтверждения из README, запущенную в новом SSH-сеансе. Если доступа нет, используйте консоль провайдера и сохранённые файлы SSH/firewall; не закрывайте последнюю рабочую сессию.
