# xray-vps-setup

Установщик Xray + Reality с Angie, панелью Marzban и Marzban-node. Основной транспорт — gRPC, дополнительный — TCP Vision. Каждый SNI относится к одному транспорту; можно добавить до четырёх дополнительных имён.

## Требования

- Ubuntu 22.04, 24.04, 26.04 или Debian 12/13; amd64 либо arm64; systemd и Bash ≥4.
- Root-доступ и рабочая консоль провайдера для восстановления.
- Все A/AAAA каждого SNI должны указывать на адреса этого VPS. NAT, CDN на входе Reality и чужие DNS-адреса автоматический сценарий не поддерживает.
- При активном UFW/firewalld/nftables нужно заранее выбрать способ интеграции firewall. Установщик не удаляет эти менеджеры и не сбрасывает чужие цепочки.

Для загрузки отдельного entry point нужны `curl`, `ca-certificates` и `python3`. Остальные зависимости устанавливаются явно. Уже установленный Docker должен иметь работающий daemon и Compose plugin; несовместимая установка Docker автоматически не заменяется.

```bash
sudo apt-get update
sudo apt-get install -y curl ca-certificates python3
curl -fL --connect-timeout 10 --max-time 60 \
  https://raw.githubusercontent.com/Jackardios/xray-vps-setup/main/vps-setup.sh \
  -o vps-setup.sh
sudo bash vps-setup.sh
```

Отдельно скачанный скрипт получает полный архив одного commit SHA и запускает установщик из этого архива. Для выбранной версии задайте `XRAY_SETUP_REVISION` полным SHA. Из полного checkout можно запускать локальный `vps-setup.sh`; шаблоны берутся из этого же checkout.

## Повторный запуск и восстановление

```bash
sudo bash vps-setup.sh repair
sudo bash vps-setup.sh reconfigure
sudo bash vps-setup.sh check
sudo bash vps-setup.sh recover
```

- `install` / запуск без аргумента: новая установка, либо сохранение существующих настроек при повторном запуске.
- `repair`: повторно подготовить и проверить конфиги с прежними ключами, UUID, паролями и путями панели. Образы остаются на сохранённых digests.
- `reconfigure`: изменить SNI, ACL и сетевые настройки, сохранив идентичность. Тип установки не меняется.
- `check`: проверить сохранённое состояние, DNS, Compose и TLS/HTTP каждого SNI; пакеты и службы не изменяются.
- `recover`: восстановить предыдущую конфигурацию после прерванного переключения. Для удалённых API-изменений node потребуется снова войти в панель. Конкурирующие изменения администратора автоматически не затираются.

Скрипт готовит файлы в `/opt/xray-vps-setup/releases/`, проверяет Xray и Angie, сохраняет предыдущую конфигурацию и переключает `current`. При обработанной ошибке возвращает предыдущие конфиги, SSH и firewall. База панели находится в отдельном `/opt/xray-vps-setup/marzban_lib`, сертификаты node — в `node_data`; они не заменяются при переключении.

Пакеты, созданный SSH-пользователь и установленные компоненты WARP не удаляются при откате. Резервные копии/старые версии не удаляются автоматически: контролируйте свободное место и хранение секретов. После жёсткого выключения или SIGKILL проверьте журнал и выполните `recover`. Два установщика одновременно работать не могут.

Первый переход со старого установщика импортирует известный standalone/panel layout и сохраняет ключи и реквизиты. Неизвестная конфигурация, старый node без состояния, split-IP/WARP панели и сторонние Compose-сервисы требуют отдельной миграции; установщик отказывает до переключения. Если пароль администратора в старом `.env` расходится с базой, исправьте это перед миграцией.

## SSH и firewall

SSH-подготовка сохраняет старые порты и прежний способ входа. Она добавляет нового sudo-пользователя с вашим ключом и новый listener, учитывая `ssh.socket`. **Root/password login ещё не отключены, пока новый вход не подтверждён.**

Откройте вторую SSH-сессию новым пользователем на выбранном порту (для split-IP — через egress IP), затем выполните из неё:

```bash
sudo --preserve-env=SSH_CONNECTION bash /opt/xray-vps-setup/lib/confirm-access.sh
```

Подтверждение проверяет пользователя, порт и адрес подключения, отключает root/password login и убирает старые разрешения из управляемой цепочки. На время этого изменения запускается таймер отката. Чужие настройки, которые мешают эффективной SSH-политике, приводят к отказу и откату.

Управляется только цепочка `XRAY_SETUP` с переходом в начале INPUT. Правила сохраняются собственным oneshot systemd-unit перед Docker. При включённой настройке SSH она разрешает SSH, ICMP, loopback, established traffic и 80/443; остальные новые входящие подключения запрещаются. Без неё сохраняется прежняя общая политика хоста, но management-порты node ограничиваются явно введёнными адресами панели.

## Панель и node

Панель стартует без скрытого статического VLESS-пользователя. Создайте пользователей в UI и назначьте им нужные inbounds. Все управляемые профили используют `fingerprint=firefox`, порт 443 и свои SNI. Пустой локальный Vision-профиль выключается; inbound резервируется для последующего добавления Vision-node.

Node требует совместимой конфигурации панели: известные tags, localhost-порты 8443/8444, Reality target `127.0.0.1:4123`, `xver=1`, ключи, shortIds и gRPC serviceName. Недостающий Vision inbound добавляется из совместимого gRPC-контракта. Перед изменениями проверяются ограничения; PUT-запросы проверяются по HTTP-статусу и чтением результата обратно.

Введите отдельно адрес node, доступный панели, и **фактические исходящие IP/CIDR панели** для ACL. Они могут отличаться от DNS панели за NAT/CDN. При смене адресов выполните `reconfigure`. Завершение node-установки требует статуса `connected` в панели.

## Split-IP, WARP и границы защиты

Split-IP и WARP поддерживаются для standalone. Панель передаёт outbound-конфиг своим узлам, поэтому host-specific source IP и localhost WARP не добавляются в общий конфиг.

Для split-IP оба разных IPv4 должны быть уже назначены VPS. DNS указывает только на ingress; несовместимые AAAA отвергаются. SSH после подтверждения разрешён через egress IPv4; Reality и HTTP challenge слушают ingress. Это меняет сетевые адреса входа и выхода, но не гарантирует анонимности и не исключает корреляцию по DNS, сертификатам или трафику. Реальный системный source проверяйте через `ip route get`, а не порядком `Address=`.

WARP включается только после успешного SOCKS-запроса. При отказе первоначальной настройки выводится предупреждение, маршруты WARP не активируются. Если уже активный WARP остановится позже, выбранные RU-домены потеряют доступ: автоматического переключения на direct нет. Другие IDN TLD и сервисы определения IP без необходимости не перенаправляются.

SNI-пул создаёт отдельные профили; клиент выбирает профиль сам. Автоматического распределения трафика и переключения транспорта нет. Разные decoy HTML не делают сайты неотличимыми от независимых сервисов. Firefox/SNI/gRPC не дают гарантии обхода любого DPI. gRPC в закреплённом Xray deprecated; переход на XHTTP должен проверяться отдельно, без скрытой смены протокола существующих клиентов.

Standalone сохраняет клиентский JSON с авторизацией SOCKS и ссылки **для каждого** SNI. Секреты/реквизиты имеют права `0600`; публичные HTML и ключи APT — `0644`. Ограничение Happ по User-Agent опционально и обходится подменой заголовка.

## Проверки проекта

```bash
python3 -m unittest discover -s tests -v
XRAY_TEST_BINARY=/absolute/path/to/xray python3 tests/transport_smoke.py
```

Для дополнительных config-test задайте `XRAY_TEST_BINARY` при запуске unittest. Для shell-тестов используйте Bash ≥4 через `BASH_TEST_BINARY`, если системный Bash старее. Проверки проекта и локальный стенд не заменяют испытания на Linux/VPS: контейнеры, выпуск/renewal ACME, reboot, новое SSH-подключение и нагрузка требуют отдельной проверки.

Ручное обслуживание описано в [install_in_docker.md](install_in_docker.md).
